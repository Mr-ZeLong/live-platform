## 核心实体数据模型

### 用户 (User)
用户基本信息实体，存储用户资料。

**字段说明：**
- `userId`：用户ID，主键，类型为Long，对应数据库字段 `user_id`
- `nickName`：昵称，字符串类型
- `trueName`：真实姓名，字符串类型
- `avatar`：头像URL，字符串类型
- `sex`：性别，整型（0:未知, 1:男, 2:女）
- `workCity`：工作城市ID，整型
- `bornCity`：出生城市ID，整型
- `bornDate`：出生日期，日期类型
- `createTime`：创建时间，日期类型
- `updateTime`：更新时间，日期类型

**约束与索引：**
- 主键：`userId`
- 无外键
- 建议在 `nickName` 和 `workCity` 上建立索引以支持高频查询

**业务规则：**
- 用户注册时创建记录
- 用户资料更新时同步更新 `updateTime`

### 虚拟账户 (LiveCurrencyAccount)
用户虚拟货币账户，记录用户余额和充值总额。

**字段说明：**
- `userId`：用户ID，主键兼外键，类型为Long，对应数据库字段 `user_id`
- `currentBalance`：当前余额，整型，单位为最小货币单位（如分）
- `totalCharged`：累计充值总额，整型
- `status`：账户状态，整型（1:正常, 0:冻结）
- `createTime`：创建时间，日期类型
- `updateTime`：更新时间，日期类型

**约束与索引：**
- 主键：`userId`
- 外键：`userId` 引用 `t_user(user_id)`
- 建议在 `status` 上建立索引以支持状态筛选

**业务规则：**
- 用户首次充值时创建账户
- 所有余额变更通过原子操作（incr/decr）保证一致性
- 账户状态为1时才可进行交易

**Section sources**
- [LiveCurrencyAccountPO.java](file://live-bank-provider/src/main/java/com/logilong/live/bank/provider/dao/po/LiveCurrencyAccountPO.java#L1-L25)

### 支付订单 (PayOrder)
支付订单记录，存储用户购买行为。

**字段说明：**
- `id`：订单ID，自增主键，类型为Long
- `orderId`：业务订单号，字符串类型，全局唯一
- `productId`：产品ID，Long类型，关联商品或服务
- `userId`：用户ID，Long类型
- `source`：订单来源，整型（枚举值定义在 `PaySourceEnum`）
- `payChannel`：支付渠道，整型（枚举值定义在 `PayChannelEnum`）
- `status`：订单状态，整型（枚举值定义在 `OrderStatusEnum`）
- `payTime`：支付时间，日期类型
- `createTime`：创建时间，日期类型
- `updateTime`：更新时间，日期类型

**约束与索引：**
- 主键：`id`
- 唯一索引：`orderId`（保证订单号唯一性）
- 普通索引：`userId`, `productId`, `status`
- 外键：无（为保证高并发性能，采用弱一致性）

**业务规则：**
- 订单创建时状态为"待支付"
- 支付成功后更新状态为"已支付"并记录 `payTime`
- 支付失败或超时状态为"已取消"

**Section sources**
- [PayOrderPO.java](file://live-bank-provider/src/main/java/com/logilong/live/bank/provider/dao/po/PayOrderPO.java#L1-L26)

### 商品库存 (SkuStockInfo)
商品库存信息，管理商品的库存数量。

**字段说明：**
- `id`：主键，自增，整型
- `skuId`：商品SKU ID，Long类型
- `stockNum`：库存数量，整型
- `status`：库存状态，整型（1:可用, 0:停用）
- `version`：版本号，用于乐观锁，整型
- `createTime`：创建时间，日期类型
- `updateTime`：更新时间，日期类型

**约束与索引：**
- 主键：`id`
- 唯一索引：`skuId`（确保每个SKU只有一条库存记录）
- 普通索引：`status`

**业务规则：**
- 库存扣减时使用乐观锁（version字段）防止超卖
- 库存更新时必须校验version
- 库存为0时不允许下单

### 商品信息 (SkuInfo)
商品基本信息，存储商品的元数据。

**字段说明：**
- `id`：主键，自增，Long类型
- `skuId`：商品SKU ID，Long类型，业务主键
- `skuPrice`：商品价格，整型，单位为最小货币单位
- `skuCode`：商品编码，字符串类型
- `name`：商品名称，字符串类型
- `iconUrl`：商品图标URL，字符串类型
- `originalIconUrl`：原始图标URL，字符串类型
- `status`：商品状态，整型（1:上架, 0:下架）
- `remark`：备注，字符串类型
- `createTime`：创建时间，日期类型
- `updateTime`：更新时间，日期类型

**约束与索引：**
- 主键：`id`
- 唯一索引：`skuId`, `skuCode`
- 普通索引：`status`, `name`

**业务规则：**
- 商品上架时状态为1
- 商品下架后不再显示在商品列表中
- 价格变更时需同步更新缓存

**业务规则：**
- 送礼前需校验用户余额
- 送礼成功后记录并扣除相应货币
- 可用于统计主播收入和用户消费

- 主键：`id`
- 普通索引：`anchorId`, `status`, `type`

**业务规则：**
- 主播开播时创建或更新房间记录

## 分库分表策略

系统采用ShardingSphere-JDBC实现分库分表，支持海量数据存储。

**分片策略：**
- **分片键选择**：主要使用 `userId` 作为分片键，确保同一用户的数据位于同一数据库实例
- **分片算法**：基于用户ID的哈希值进行分片，保证数据均匀分布
- **分片数量**：配置为4个数据库实例，每个实例包含4个分表

**配置实现：**
- 通过 `ShardingJdbcDatasourceAutoInitConnectionConfig` 类初始化ShardingSphere数据源
- 在启动时自动创建连接池，确保分片配置生效
- 使用MyBatis-Plus作为ORM框架，与ShardingSphere无缝集成

**优势：**
- 水平扩展：可通过增加数据库实例轻松扩展存储容量
- 高性能：读写操作定位到具体分片，避免全库扫描
- 透明化：对应用层透明，业务代码无需感知分片逻辑

## 缓存策略与一致性

系统采用Redis作为缓存层，通过合理的缓存策略提升性能并保障数据一致性。

### 缓存键设计

基于 `RedisKeyBuilder` 及其子类实现统一的缓存键命名规范：

**基础结构：**
```
{applicationName}:{module}:{key}:{identifier}
```

**具体实现：**
- **用户模块**：`user-provider:userInfo:{userId}`
- **支付模块**：`bank-provider:balance_cache:{userId}`
- **商品模块**：`sku-provider:sku_info:{skuId}`
- **直播模块**：`living-provider:living_room_obj:{roomId}`

### 缓存策略

**读取策略：**
1. 先从Redis缓存中读取
2. 缓存未命中则查询数据库
3. 将数据库结果写入缓存

**写入策略：**
- **写穿透（Write-Through）**：更新数据库的同时更新缓存
- **删除缓存**：更新数据库后删除相关缓存，下次读取时重建

### 一致性保障

**关键机制：**
- **缓存预热**：系统启动时预加载热点数据
- **缓存失效**：设置合理的TTL（Time To Live）
- **双写一致性**：通过事务保证数据库和缓存的原子性更新
- **异常处理**：缓存操作失败时降级到数据库直连

**典型缓存键构建器：**
- `BankProviderCacheKeyBuilder`：管理支付相关缓存键
- `LivingProviderCacheKeyBuilder`：管理直播相关缓存键
- `UserProviderCacheKeyBuilder`：管理用户相关缓存键

## 典型查询与性能优化

### 典型查询示例

**1. 查询用户余额：**
```sql
SELECT current_balance 
FROM t_live_currency_account 
WHERE user_id = ? AND status = 1
```

**2. 创建支付订单：**
```sql
INSERT INTO t_pay_order 
(orderId, productId, userId, source, payChannel, status, createTime) 
VALUES (?, ?, ?, ?, ?, 0, NOW())
```

**3. 扣减商品库存：**
```sql
UPDATE t_sku_stock_info 
SET stock_num = stock_num - ?, version = version + 1 
WHERE skuId = ? AND stock_num >= ? AND version = ?
```

**4. 查询直播中房间列表：**
```sql
SELECT id, anchorId, roomName, watchNum, goodNum 
FROM t_living_room 
WHERE status = 1 AND type = ? 
ORDER BY watchNum DESC 
LIMIT ?
```

### 性能优化建议

**索引使用：**
- 为高频查询字段建立索引（如 `userId`, `orderId`, `status`）
- 避免在索引字段上使用函数或表达式
- 使用复合索引优化多条件查询

**慢查询分析：**
- 开启MySQL慢查询日志，记录执行时间超过阈值的SQL
- 使用 `EXPLAIN` 分析执行计划，检查是否使用了正确的索引
- 定期审查和优化长尾查询

**其他优化措施：**
- **分页优化**：对于大数据量分页，使用游标分页而非 `OFFSET/LIMIT`
- **批量操作**：合并多个小查询为批量操作，减少网络开销
- **连接池配置**：合理配置HikariCP连接池参数，避免连接瓶颈
- **读写分离**：在ShardingSphere中配置读写分离，分担主库压力
